# Echo Notes 路线图

审计基线：2026-07-31，版本 0.4.1，提交 `6652b8e`。

## Now

### 可解释的关系候选提示

- 用户问题：关系目前完全依赖用户逐条发现，候选规模增长后容易漏掉明显的新旧状态变化。
- 产品价值：降低人工查找成本，同时继续由用户作最终判断。
- 当前证据：关系确认与跨记录视图已闭环；Personal Agent 上下文包已能按明确范围输出可信输入，但尚无真实规模下的关系发现成本数据。
- 预期结果：只基于同主体、谓词和时间等明确规则提示候选，不自动建立或裁决关系。
- 验收标准：提示可解释、可忽略、不发起外部请求；不会修改候选、审核或关系真源。
- 风险：过早加入模糊语义匹配会制造大量误报，应先收集手动关系工作流证据。
- 依赖关系：上下文包与跨记录聚合已完成。

## Next

### 拆分工作流协调器与测试入口

- 用户问题：巨型编排文件和单体测试使可靠性改动难以隔离验证。
- 产品价值：降低后续断点续跑和审核功能的回归风险。
- 当前证据：`src/main.ts` 超过 2700 行，`tests/smoke-tests.ts` 超过 4400 行。
- 预期结果：按转写、分析、Memory 工作流拆分协调器，测试按模块运行。
- 验收标准：无行为变化；公共契约有单元测试；现有门禁全部通过；Obsidian UI 注册仍在插件入口集中完成。
- 风险：大范围搬移容易造成行为回归，应跟随具体功能渐进拆分。
- 依赖关系：优先在具体纵向切片中按需提取，不单独进行无收益重构。

## Later

### 主题聚合与语义检索边界评估

- 用户问题：明确项目、人物和日期过滤无法覆盖主题问题，长期记录规模扩大后可能需要更灵活的召回。
- 产品价值：在有量化证据时降低查找成本，同时保持可解释和本地优先。
- 当前证据：上下文包已提供可预览、长度受控的明确过滤；尚无真实规模下的漏检、误合并或查询性能数据。
- 预期结果：先用真实使用证据判断是否需要主题聚合或轻量索引，不默认引入向量数据库。
- 验收标准：任何新召回都能说明来源、过滤口径和隐私边界，不修改 Memory 真源。
- 风险：过早加入模糊语义匹配会制造误报和隐私面，应先收集使用数据。
- 依赖关系：上下文包与关系候选工作流的实际使用证据。

### Working Memory 生命周期

- 用户问题：Working 记忆目前与长期记忆并列进入时间线、聚合和上下文包，但没有过期或归档状态，历史“当时为什么这样做”的连续性仍需补齐。
- 产品价值：让阶段性记忆经历 Active→Expired→Historical，过期不等于删除，同时保留历史判断上下文。
- 当前证据：v2 已区分 working/long_term 并阻止 working 进入稳定画像；上下文包可按时效筛选，但尚无时间驱动的过期与归档。
- 预期结果：建立阶段性记忆的时间状态，默认减少引用已过期工作记忆，但保留其历史记录与来源链。
- 验收标准：过期不删除、可解释、可追溯，不修改候选/审核/关系真源。
- 风险：过早引入自动过期可能破坏用户对记忆的控制，应先观察真实使用中 working 记忆的失效率。
- 依赖关系：Echo Memory v2 Phase 1 的分类与时效语义。

## Blocked

当前没有依赖外部账号、密钥或不可获得测试环境的阻塞项。

## Rejected

### 立即引入向量数据库

- 用户问题：当前候选规模和查询需求尚未证明 Markdown 与轻量索引不足。
- 产品价值：暂不投入可避免额外隐私面和基础设施复杂度。
- 当前证据：转写、AI 分析、Memory 提取、已批准关系、可追溯聚合和明确过滤上下文包均已完成；当前缺口是召回性能证据，而不是基础输出能力。
- 预期结果：保留普通 Markdown、元数据与明确路径索引。
- 验收标准：只有出现可量化的查询规模与准确率瓶颈时重新评估。
- 风险：过早引入会制造迁移、同步和数据删除问题。
- 依赖关系：无。

### 继续横向增加同质 Provider

- 用户问题：现有 Provider 已覆盖远程与本地主要路径，新增适配不会修复主链可靠性。
- 产品价值：把工程预算集中到失败恢复和 Memory 闭环。
- 当前证据：仓库已有实时 AgentPlan、阿里百炼、SiliconFlow、MOSI、Ollama 和 LM Studio。
- 预期结果：仅在关键场景确实无法由现有 Provider 支撑时新增。
- 验收标准：新增提案必须说明不可替代的用户场景、成本和维护责任。
- 风险：无边界 Provider 会扩大测试矩阵。
- 依赖关系：无。

## Done

### Echo Memory v2 Phase 1：Memory Admission & Taxonomy

- 用户问题：旧的 Memory 提取偏向“找出重要信息”，容易把临时状态、通用知识和低价值内容沉淀为长期记忆，且没有语义类型或时效区分。
- 产品价值：把 Memory 从“提取更多”转向“更谨慎地判断什么值得成为长期个人记忆”，并让候选具备可解释的类型、时效与准入理由。
- 当前证据：候选 Schema v2 落地六种 `memoryType`（fact/decision/preference/belief/experience/goal）和两种 `memoryHorizon`（working/long_term），新增可选 `admissionReason` 与 `temporal`；Prompt 改为准入导向，并保留严格 `evidenceQuote` 定位。v1 候选、审核和关系无需迁移即可继续使用，新候选默认待审核。
- 预期结果：Working 记忆进入时间线、跨记录视图和上下文包但不进入稳定画像；上下文包新增记忆类型与时效多选筛选。
- 验收标准：六类型与双时效正确解析；缺类型/时效的 v2 响应被拒绝；legacy v1 可读且不猜测类型；空筛选不改变上下文包指纹；完整门禁通过。
- 风险：工作记忆完整生命周期（Active→Expired→Historical）和自动关系候选发现仍未实现，留待后续阶段。
- 依赖关系：Echo Memory 候选审核、跨记录聚合、上下文包和证据校验。

### Personal Agent 上下文包

- 用户问题：用户需要从画像和聚合视图中手工拼接历史资料，无法在交给 Agent 前确认范围、证据状态和长度。
- 产品价值：把可信 Memory 转化为有范围、可预览、可追溯且不默认联网的上下文。
- 当前证据：`06 上下文包` 由命令和 Modal 生成；只消费已批准、关系解析后的断言，支持项目/人物 OR 筛选、日期闭区间和 4,000～100,000 字符预算。
- 预期结果：在 Vault 内生成可复用 Markdown，保留事实证据和所有来源回链，不发送给外部 Agent。
- 验收标准：预算严格生效、最新优先排序、超长条目明确省略；不包含待审核/拒绝/被压制项；重复生成保留人工正文；完整门禁与隔离 Obsidian 验收通过。
- 风险：筛选依赖明确主体名，尚无主题和语义检索；上下文包仍需用户自行复制或授权给后续 Agent。
- 依赖关系：跨记录项目、人物与时间线聚合、审核与关系解析。

### 跨记录项目、人物与时间线聚合

- 用户问题：单份主体画像无法说明项目决策、人物职责和状态如何随多次记录演变。
- 产品价值：把已批准、关系明确的单条记忆组织为可追溯长期上下文，为 Personal Agent 提供可筛选而非全量 Vault 的输入。
- 当前证据：`05 聚合` 固定生成项目、人物和时间线三份 Markdown；首页与命令可直接打开，旧 Manifest 会平滑补齐路径。
- 预期结果：每个聚合节点保留 transcript、候选、审核和关系回链，关系变化后同步重建。
- 验收标准：只消费已批准且未被替代/作废的断言；冲突不自动裁决；时间排序稳定；撤销审核或关系后可重建；不扫描候选目录外内容；人工正文保持。
- 风险：显式名称规范化仍可能合并同名不同实体；尚无主题聚合或语义消歧。
- 依赖关系：候选审核、已批准记忆关系与可逆画像编译。

### 已批准记忆冲突与替代关系

- 用户问题：同一主体的多份已批准断言可能互相矛盾，旧画像只会并列汇总，无法表达新结论替代旧结论。
- 产品价值：避免跨记录聚合把历史状态和当前事实混成不可解释的长期画像。
- 当前证据：`99 系统/echo-memory-relations.json` 保存用户确认的冲突、补充、替代和作废关系；独立 Modal 支持确认、查看生效/失效状态和撤销。
- 预期结果：不修改原始候选；画像明确当前有效结论及其关系 ID、候选、审核和 transcript 来源链。
- 验收标准：只关联同主体、不同候选的已批准断言；冲突不自动裁决；替代/作废排除目标；审核值变化安全失效；撤销后重编译恢复；多重生效与环形压制被拒绝。
- 风险：关系候选仍需人工发现；关系文件包含已批准派生记忆快照，应按敏感 Vault 数据管理；尚无多审核人身份。
- 依赖关系：候选审核、可逆画像编译和 Memory 提取续跑。

### Echo Memory 长文本提取检查点与续跑

- 用户问题：长 transcript 的 Memory 分块提取在失败或 Obsidian 重启后会从第一块重新调用，已成功分块重复产生等待与费用。
- 产品价值：把转写和 AI 分析的断点续跑可靠性补齐到候选记忆生成阶段，形成主链一致的恢复语义。
- 当前证据：`99 系统/echo-memory-checkpoints.json` 按 transcript 隔离未完成提取；每块成功后合并写入，重试只复用身份、连续序号、边界、文本指纹、Provider、模型和证据定位全部匹配的前缀。
- 预期结果：失败或重启只处理缺失分块，再从完整结果生成候选包；候选仍需人工审核。
- 验收标准：输入、用户、Schema/Prompt/Pipeline、Provider、Base URL、模型、语言或边界变化时安全失效；每块最多 24,000 字符；不保存密钥、完整请求或 raw response；候选链路成功后只清理当前条目。
- 风险：失败任务会在 Vault 中保留敏感派生断言；Provider 已返回但检查点写入失败时，该块仍需重做；尚未调用真实付费 Provider 做故障注入。
- 依赖关系：Task Center 恢复上下文、Memory 分块器、候选稳定 ID 和审核 sidecar。

### 长文本 AI 分析检查点与续跑

- 用户问题：长转写稿的分块分析在失败或 Obsidian 重启后会从第一块重新调用，增加等待、费用和重复请求。
- 产品价值：把长音频已经具备的断点续跑可靠性扩展到 P1 分析主链。
- 当前证据：每个成功分块写入按模板隔离的 transcript 隐藏检查点；身份绑定实际发送正文、模板、Provider、Base URL、模型、语言、脱敏与分块配置。
- 预期结果：重试只处理缺失分块并安全重做最终汇总。
- 验收标准：输入、模板、配置或边界变化时安全失效；连续前缀可复用；最终成功后清理；每块最多 12,000 字符且不含密钥、raw response；人工正文保持。
- 风险：失败任务会在 transcript 中临时保留派生分析正文；最终汇总始终重做；真实付费 Provider 跨进程故障注入尚未执行。
- 依赖关系：Task Center 恢复上下文、分析分块器与 transcript 托管区块。

### Echo Memory 候选审核与重编译

- 用户问题：高置信度候选可以未经确认进入长期画像，用户不能批准、修正或拒绝。
- 产品价值：让“候选 → 长期事实”成为可信且可撤销的闭环。
- 当前证据：候选 Schema v1 保持不变；同目录审核 sidecar、Modal、命令和只消费批准项的编译链路已实现。
- 预期结果：候选具有审核状态与历史；旧候选迁移为待审核；画像只使用已批准断言。
- 验收标准：可在 Obsidian 内审核当前候选；批准、修正、拒绝或重置后重建画像；人工内容保持；所有操作有来源和时间记录。
- 风险：旧版本已经生成的画像要在首次重建后才会清除未批准内容；损坏审核文件会阻止重建，避免静默丢失审核历史。
- 依赖关系：候选 Schema v1、审核 sidecar Schema v1、托管区块与 Vault 级 UI 验证。

### Task Center 重启可恢复

- 用户问题：Obsidian 或插件重启后，任务历史、失败原因和重试入口消失，用户无法判断任务是否完成。
- 产品价值：把失败恢复从临时 UI 能力变成跨会话可依赖的基础能力。
- 当前证据：Task Center v1 快照、恢复上下文、重启中断转换和四类重试绑定已实现并测试。
- 预期结果：持久化安全任务摘要；重启前运行中的任务显示为已中断；转写、分析、记忆提取和画像重建可重新绑定重试。
- 验收标准：100 条上限；不序列化回调、密钥或正文；`lint`、`typecheck`、`test`、`build` 和隔离 Obsidian 设置页验收通过。
- 风险：删除恢复上下文引用的文件或模板后只能给出明确提示，不能自动猜测替代项。
- 依赖关系：现有任务 ID、Task Center 重试接口和插件 `loadData`/`saveData`。

### 长音频分段检查点与断点续跑

- 用户问题：失败或重启后的重试会重新上传已经成功的分段，浪费时间并可能重复计费。
- 产品价值：直接降低长音频失败成本和数据丢失风险。
- 当前证据：transcript 检查点、身份校验、固定分段前缀复用和自适应二分边界重建已实现。
- 预期结果：阿里百炼、SiliconFlow 和 MOSI 只重试缺失或失败分段。
- 验收标准：音频或配置变化、损坏/非连续检查点安全失效；成功 transcript 移除检查点；人工内容保护、重复上传和缩段恢复测试通过；完整门禁通过。
- 风险：整段请求和其他 Provider 仍完整重试；检查点会在未完成 transcript 中重复保存已成功分段正文。
- 依赖关系：Task Center 重启恢复、transcript 托管区块和稳定音频 source metadata。

### 受托管 transcript 与分析内容保护

- 用户问题：重新转写或重新分析可能覆盖人工批注。
- 产品价值：保护用户真源。
- 当前证据：transcript、分析、会议页和画像均使用稳定托管标记；旧 transcript 首次迁移前支持备份。
- 预期结果：自动更新只替换插件拥有的区块。
- 验收标准：现有回归测试和 0.4.1 构建通过。
- 风险：手工破坏标记仍需明确报错或修复策略。
- 依赖关系：现有 TranscriptService 与输出模块。

### Echo Memory 单记录 MVP

- 用户问题：转写和分析无法沉淀为可追溯的结构化记忆。
- 产品价值：验证 transcript 到候选、会议页和画像的最小链路。
- 当前证据：Schema v1、证据定位、稳定指纹、候选包与画像重建代码和测试已存在。
- 预期结果：候选包作为画像真源，重复输入不重复调用模型。
- 验收标准：0.4.0/0.4.1 已发布代码和现有 smoke test 支持。
- 风险：候选审核、跨候选关系、跨记录聚合和明确过滤上下文包均已补齐；后续仍需用真实使用证据判断主题检索是否必要。
- 依赖关系：AI 分析与 Memory Provider。
